# Mbia MVP — Data Model

**Version:** 0.2  
**Status:** Draft for implementation  
**Database:** PostgreSQL 18  
**Scope:** Commercial MVP

## 1. Purpose

This document is the technical source of truth for the relational persistence model of the Mbia MVP.

It translates the product concepts into a PostgreSQL model while preserving the following rules:

- a `User` is not a `Person`;
- a `Family` is the primary data-isolation boundary;
- only explicit genealogical facts are persisted;
- derived kinship is computed from explicit facts;
- important destructive operations are reversible;
- important mutations are auditable;
- concurrent edits must not silently overwrite each other;
- the schema must remain readable and maintainable by a human developer.

## 2. General conventions

### 2.1 Identifiers

All public/domain identifiers use UUIDs.

```text
UUID generated by the application or PostgreSQL gen_random_uuid()
```

Sequential database identifiers must not be exposed through public APIs.

### 2.2 Timestamps

All timestamps use `TIMESTAMPTZ` and are stored in UTC.

Typical columns:

```text
created_at
updated_at
archived_at
occurred_at
```

### 2.3 Optimistic locking

Mutable aggregate tables contain:

```text
version BIGINT NOT NULL DEFAULT 0
```

The API exposes the current version. Mutating use cases must compare the expected version with the persisted version before committing.

### 2.4 Soft lifecycle

Entities that must remain recoverable use explicit statuses instead of physical deletion.

Examples:

```text
Person: ACTIVE | ARCHIVED | MERGED
Relationship: ACTIVE | ARCHIVED
Membership: ACTIVE | REMOVED
Memory: ACTIVE | ARCHIVED
```

### 2.5 Family isolation

Every family-scoped table contains `family_id`.

Where practical, composite foreign keys `(resource_id, family_id)` are used to prevent cross-family references at database level in addition to application-level authorization.

### 2.6 Naming

Database names use `snake_case`.

Java domain objects use explicit value objects such as:

```text
FamilyId
PersonId
MemoryId
RelationshipId
```

## 5. Table: `users`

Represents a Mbia account. Authentication credentials are owned by the external identity provider.

```sql
users (
    id                         UUID PRIMARY KEY,
    identity_provider_subject  VARCHAR(255) NOT NULL UNIQUE,
    email                      VARCHAR(320),
    display_name               VARCHAR(200),
    preferred_locale           VARCHAR(5) NOT NULL DEFAULT 'fr',
    status                     VARCHAR(20) NOT NULL DEFAULT 'ACTIVE',
    deleted_at                 TIMESTAMPTZ,
    created_at                 TIMESTAMPTZ NOT NULL,
    updated_at                 TIMESTAMPTZ NOT NULL,
    version                    BIGINT NOT NULL DEFAULT 0,

    CHECK (preferred_locale IN ('fr', 'en')),
    CHECK (status IN ('ACTIVE', 'DELETED')),
    CHECK (status = 'DELETED' OR email IS NOT NULL)
)
```

Recommended indexes:

```sql
CREATE UNIQUE INDEX uq_users_email_lower
ON users (lower(email))
WHERE status = 'ACTIVE';
```

Notes:

- `identity_provider_subject` is the stable OIDC `sub` claim from Keycloak (ADR-005).
- Rows are created just-in-time on the first authenticated API call; `email`, `display_name` and `preferred_locale` are initialised from token claims.
- Mbia does not store password hashes.
- Email uniqueness applies to active accounts.
- Account deletion (product/mvp.md §30) anonymises the row: `status = DELETED`, `email = NULL`, `display_name = NULL`, `identity_provider_subject = 'deleted:' || id`, `deleted_at` set. Foreign keys to the user remain valid; the UI displays "Former member".

## 6. Table: `families`

Represents one private collaborative family space.

```sql
families (
    id            UUID PRIMARY KEY,
    name          VARCHAR(200) NOT NULL,
    status        VARCHAR(30) NOT NULL DEFAULT 'ACTIVE',
    created_by    UUID NOT NULL REFERENCES users(id),
    created_at    TIMESTAMPTZ NOT NULL,
    updated_at    TIMESTAMPTZ NOT NULL,
    version       BIGINT NOT NULL DEFAULT 0
)
```

Rules:

- the creator automatically receives an `ADMIN` membership;
- a family is private by default;
- all family-scoped API queries must verify active membership first.

## 7. Table: `family_memberships`

Represents access granted to a user for one family.

```sql
family_memberships (
    id            UUID PRIMARY KEY,
    family_id     UUID NOT NULL REFERENCES families(id),
    user_id       UUID NOT NULL REFERENCES users(id),
    role          membership_role NOT NULL,
    status        membership_status NOT NULL DEFAULT 'ACTIVE',
    joined_at     TIMESTAMPTZ NOT NULL,
    removed_at    TIMESTAMPTZ,
    created_at    TIMESTAMPTZ NOT NULL,
    updated_at    TIMESTAMPTZ NOT NULL,
    version       BIGINT NOT NULL DEFAULT 0,

    UNIQUE (family_id, user_id)
)
```

Recommended indexes:

```sql
CREATE INDEX idx_memberships_user_active
ON family_memberships (user_id, status);

CREATE INDEX idx_memberships_family_active
ON family_memberships (family_id, status);
```

Rules:

- only `ACTIVE` memberships grant access;
- changing a membership role is an audited operation;
- removing a membership does not delete the user or family data;
- removing a membership (removal by ADMIN or leaving) sets `linked_user_id = NULL` on the User's Person in that Family, in the same transaction, with an audit entry;
- a Family must keep at least one ACTIVE `ADMIN` membership; the use case locks the Family's ADMIN memberships before removing or demoting one (`LAST_ADMIN_REQUIRED`);
- accepting a new invitation for a `REMOVED` membership reactivates the existing row (`status = ACTIVE`, new role, new `joined_at`, `removed_at = NULL`).

## 8. Table: `family_invitations`

Represents an invitation sent before a membership exists.

```sql
family_invitations (
    id                 UUID PRIMARY KEY,
    family_id          UUID NOT NULL REFERENCES families(id),
    channel            invitation_channel NOT NULL,
    email              VARCHAR(320),
    locale             VARCHAR(5) NOT NULL,
    role               membership_role NOT NULL,
    token_hash         VARCHAR(255) NOT NULL UNIQUE,
    status             invitation_status NOT NULL DEFAULT 'PENDING',
    invited_by         UUID NOT NULL REFERENCES users(id),
    accepted_by        UUID REFERENCES users(id),
    revoked_by         UUID REFERENCES users(id),
    expires_at         TIMESTAMPTZ NOT NULL,
    accepted_at        TIMESTAMPTZ,
    revoked_at         TIMESTAMPTZ,
    renewed_at         TIMESTAMPTZ,
    created_at         TIMESTAMPTZ NOT NULL,
    updated_at         TIMESTAMPTZ NOT NULL,
    version            BIGINT NOT NULL DEFAULT 0,

    CHECK (channel <> 'EMAIL' OR email IS NOT NULL),
    CHECK (role <> 'ADMIN'),
    CHECK (locale IN ('fr', 'en'))
)
```

Rules:

- only `ADMIN` may invite;
- the raw token is 32 random bytes from a CSPRNG, base64url-encoded; only its SHA-256 hash is stored; the raw token is returned once, in the creation or renewal response;
- `expires_at = created_at + 14 days` (or `renewed_at + 14 days` after renewal);
- the invitation is not bound to `email`: any authenticated, email-verified User holding the raw token may accept it;
- accepting an invitation atomically creates or reactivates the membership and marks the invitation `ACCEPTED` (single use);
- if the accepting User already has an `ACTIVE` membership in the Family, nothing changes and the invitation stays `PENDING`;
- renewal replaces `token_hash`, resets `expires_at`, sets `renewed_at` and, for `EMAIL`, sends the email again; the old token stops working immediately;
- revocation sets `status = REVOKED`, `revoked_at`, `revoked_by`;
- `EXPIRED` is set lazily when an expired `PENDING` invitation is read or accepted, and may also be set by a scheduled task;
- `role = ADMIN` is not allowed in MVP;
- expired, revoked or accepted invitations cannot be accepted.

Recommended partial index:

```sql
CREATE INDEX idx_invitations_family_pending
ON family_invitations (family_id, lower(email))
WHERE status = 'PENDING';
```

## 9. Partial-date representation

Mbia must not invent exact dates for uncertain genealogy data.

Dates are represented by three columns per date concept:

```text
*_date       DATE nullable
*_year       SMALLINT nullable
*_precision  date_precision NOT NULL
```

Invariant:

```text
EXACT     => date != null, year = extracted year or null by convention
YEAR_ONLY => date = null, year != null
UNKNOWN   => date = null, year = null
```

The preferred implementation keeps only one source of truth:

```text
EXACT     => *_date populated, *_year null
YEAR_ONLY => *_date null, *_year populated
UNKNOWN   => both null
```

## 10. Table: `persons`

Represents an individual documented inside one family graph.

```sql
persons (
    id                       UUID PRIMARY KEY,
    family_id                UUID NOT NULL REFERENCES families(id),

    first_name               VARCHAR(150) NOT NULL,
    middle_names             VARCHAR(250),
    last_name                VARCHAR(150),
    preferred_name           VARCHAR(150),

    gender                   gender NOT NULL DEFAULT 'UNKNOWN',

    birth_date               DATE,
    birth_year               SMALLINT,
    birth_date_precision     date_precision NOT NULL DEFAULT 'UNKNOWN',

    is_deceased              BOOLEAN NOT NULL DEFAULT FALSE,
    death_date               DATE,
    death_year               SMALLINT,
    death_date_precision     date_precision NOT NULL DEFAULT 'UNKNOWN',

    profile_media_asset_id   UUID,
    biography                TEXT,

    linked_user_id           UUID REFERENCES users(id),

    status                   person_status NOT NULL DEFAULT 'ACTIVE',
    merged_into_person_id    UUID,

    created_by               UUID NOT NULL REFERENCES users(id),
    updated_by               UUID NOT NULL REFERENCES users(id),
    created_at               TIMESTAMPTZ NOT NULL,
    updated_at               TIMESTAMPTZ NOT NULL,
    archived_at              TIMESTAMPTZ,
    version                  BIGINT NOT NULL DEFAULT 0,

    UNIQUE (id, family_id)
)
```

`profile_media_asset_id` and its foreign key are created by the migration that introduces `media_assets`; the `persons` migration does not create them. The self-referencing merge foreign key is created with the table.

Additional foreign keys:

```sql
ALTER TABLE persons
ADD CONSTRAINT fk_person_profile_media
FOREIGN KEY (profile_media_asset_id, family_id)
REFERENCES media_assets(id, family_id);

ALTER TABLE persons
ADD CONSTRAINT fk_person_merged_target
FOREIGN KEY (merged_into_person_id, family_id)
REFERENCES persons(id, family_id);
```

Recommended constraints:

```text
first_name must not be blank

is_deceased = false
  => death_date is null
  => death_year is null
  => death_date_precision = UNKNOWN

status = MERGED
  => merged_into_person_id is not null

status != MERGED
  => merged_into_person_id is null

id != merged_into_person_id
```

Date precision constraints should enforce the rules from section 9.

Recommended indexes:

```sql
CREATE INDEX idx_persons_family_status
ON persons (family_id, status);

CREATE INDEX idx_persons_family_name
ON persons (family_id, lower(last_name), lower(first_name));

CREATE UNIQUE INDEX uq_person_linked_user_per_family
ON persons (family_id, linked_user_id)
WHERE linked_user_id IS NOT NULL AND status <> 'MERGED';
```

Rules:

- a user may represent at most one person per family;
- a person may represent at most one user;
- an active linked person cannot be archived without first unlinking it;
- a `MERGED` person cannot receive new relationships or memories;
- `first_name` is the only required human-name field for MVP.

## 11. Table: `family_relationships`

Stores only explicit genealogical facts.

```sql
family_relationships (
    id                 UUID PRIMARY KEY,
    family_id          UUID NOT NULL REFERENCES families(id),
    type               relationship_type NOT NULL,
    source_person_id   UUID NOT NULL,
    target_person_id   UUID NOT NULL,
    status             relationship_status NOT NULL DEFAULT 'ACTIVE',
    created_by         UUID NOT NULL REFERENCES users(id),
    updated_by         UUID NOT NULL REFERENCES users(id),
    created_at         TIMESTAMPTZ NOT NULL,
    updated_at         TIMESTAMPTZ NOT NULL,
    archived_at        TIMESTAMPTZ,
    version            BIGINT NOT NULL DEFAULT 0,

    CHECK (source_person_id <> target_person_id),

    FOREIGN KEY (source_person_id, family_id)
        REFERENCES persons(id, family_id),

    FOREIGN KEY (target_person_id, family_id)
        REFERENCES persons(id, family_id),

    UNIQUE (id, family_id)
)
```

### 11.1 Direction semantics

```text
PARENT_OF:
  source_person_id = parent
  target_person_id = child

PARTNER_OF:
  symmetric relation
```

### 11.2 Canonical partner ordering

To guarantee uniqueness for symmetric partner relations, the application must canonicalize UUID order before persistence:

```text
for PARTNER_OF:
source_person_id < target_person_id
```

Recommended database check:

```sql
CHECK (
  type <> 'PARTNER_OF'
  OR source_person_id < target_person_id
)
```

### 11.3 Active relation uniqueness

```sql
CREATE UNIQUE INDEX uq_active_parent_relationship
ON family_relationships (
    family_id,
    type,
    source_person_id,
    target_person_id
)
WHERE status = 'ACTIVE' AND type = 'PARENT_OF';

CREATE UNIQUE INDEX uq_active_partner_relationship
ON family_relationships (
    family_id,
    type,
    source_person_id,
    target_person_id
)
WHERE status = 'ACTIVE' AND type = 'PARTNER_OF';
```

### 11.4 Graph rules not enforceable by simple constraints

Application/domain logic must additionally guarantee:

```text
no parental cycle
no relationship involving ARCHIVED/MERGED persons
no duplicate active relation
no cross-family relation
```

Probable date inconsistencies produce warnings, not database failures.

## 12. Derived kinship

The following are **not persisted as facts**:

```text
CHILD_OF
SIBLING_OF
GRANDPARENT_OF
GRANDCHILD_OF
UNCLE_OF
AUNT_OF
NEPHEW_OF
NIECE_OF
FIRST_COUSIN_OF
```

They are computed from active `PARENT_OF` relations.

This ensures that removing a parent relation automatically changes all dependent kinship results.

## 13. Table: `media_assets`

Stores metadata about binary files held in S3-compatible object storage.

```sql
media_assets (
    id                  UUID PRIMARY KEY,
    family_id           UUID NOT NULL REFERENCES families(id),
    purpose                 media_purpose NOT NULL,
    status                  media_status NOT NULL DEFAULT 'PENDING_UPLOAD',
    upload_storage_key      VARCHAR(1024) NOT NULL UNIQUE,
    display_storage_key     VARCHAR(1024) UNIQUE,
    thumbnail_storage_key   VARCHAR(1024) UNIQUE,
    original_filename       VARCHAR(500),
    upload_mime_type        VARCHAR(100) NOT NULL,
    upload_size_bytes       BIGINT NOT NULL,
    width_px                INTEGER,
    height_px               INTEGER,
    failure_reason          VARCHAR(100),
    uploaded_by             UUID NOT NULL REFERENCES users(id),
    created_at              TIMESTAMPTZ NOT NULL,
    ready_at                TIMESTAMPTZ,
    archived_at             TIMESTAMPTZ,

    CHECK (upload_size_bytes > 0 AND upload_size_bytes <= 15728640),
    CHECK (status <> 'READY'
           OR (display_storage_key IS NOT NULL AND thumbnail_storage_key IS NOT NULL)),

    UNIQUE (id, family_id)
)
```

MVP supported upload MIME types:

```text
image/jpeg
image/png
image/webp
```

Rules (processing details: ADR-007):

- an asset starts as `PENDING_UPLOAD`; the browser uploads to `upload_storage_key`;
- `completeMediaUpload` validates and processes the upload synchronously, writes the `display` and `thumbnail` JPEG derivatives without metadata, deletes the uploaded original, and sets `READY`; `width_px`/`height_px` describe the display derivative;
- on validation failure the asset becomes `FAILED` with a `failure_reason`;
- `PENDING_UPLOAD` assets older than 24 hours become `FAILED` and their objects are deleted by a scheduled task;
- only `READY` media may be attached to a person profile or photo memory;
- storage keys are internal and must not be exposed as public permanent URLs;
- views use pre-signed GET URLs valid for 60 minutes.

Stores both stories and photo memories.

```sql
memories (
    id                  UUID PRIMARY KEY,
    family_id           UUID NOT NULL REFERENCES families(id),
    type                memory_type NOT NULL,
    status              memory_status NOT NULL DEFAULT 'ACTIVE',

    title               VARCHAR(250),
    content             TEXT,
    caption             TEXT,
    media_asset_id      UUID,

    taken_date          DATE,
    taken_year          SMALLINT,
    taken_date_precision date_precision NOT NULL DEFAULT 'UNKNOWN',

    created_by          UUID NOT NULL REFERENCES users(id),
    updated_by          UUID NOT NULL REFERENCES users(id),
    created_at          TIMESTAMPTZ NOT NULL,
    updated_at          TIMESTAMPTZ NOT NULL,
    archived_at         TIMESTAMPTZ,
    version             BIGINT NOT NULL DEFAULT 0,

    FOREIGN KEY (media_asset_id, family_id)
        REFERENCES media_assets(id, family_id),

```

Type invariants:

```text
PHOTO:
  media_asset_id required
  title optional
  content must be null
  caption optional

STORY:
  title required
  content required
  media_asset_id null in MVP
  caption null
```

A memory must be associated with at least one active person in MVP. This is enforced in the application transaction because it spans `memory_persons`.

## 15. Table: `memory_persons`

Many-to-many association between memories and persons.

```sql
memory_persons (
    family_id   UUID NOT NULL,
    memory_id   UUID NOT NULL,
    person_id   UUID NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL,

    PRIMARY KEY (memory_id, person_id),

    FOREIGN KEY (memory_id, family_id)
        REFERENCES memories(id, family_id),

    FOREIGN KEY (person_id, family_id)

```

Rules:

- a photo/story can reference multiple people;
- no duplicate association;
- a `MERGED` source person must be replaced with the merge target during merge;

## 19. Merge Persons transaction

Merging source Person `B` into target Person `A` is one atomic transaction.

Preconditions:

```text
A.family_id == B.family_id
A.status == ACTIVE
B.status == ACTIVE
A.id != B.id

not (A.linked_user_id != null
     and B.linked_user_id != null
     and A.linked_user_id != B.linked_user_id)
```

Transaction steps:

1. lock both Person rows;
2. verify expected versions;
3. retain target scalar values when both source and target are non-empty; fill only empty target fields from source (empty: absent text, `gender = UNKNOWN`, date precision `UNKNOWN`; the target is deceased when either is, and an unknown target death date takes the source's, OQ-028);
4. move `memory_persons` links from B to A, deduplicating existing links;
5. move relationships from B to A, ACTIVE and ARCHIVED (OQ-027); an ARCHIVED relation between A and B stays on B;
6. canonicalize `PARTNER_OF` relations after replacement;
7. deduplicate identical resulting relations: an ACTIVE relation of B identical to an ACTIVE relation of A is archived and stays on B;
8. reject any resulting self relation (an ACTIVE relation between A and B);
9. reject any resulting parental cycle;
10. transfer linked user only when unambiguous: B's user moves to A when A has none, and B keeps no linked user;
11. mark B as `MERGED`;
12. set `B.merged_into_person_id = A.id`;
13. write audit entries;
14. commit.

No partial merge may remain persisted. Refusals answer `PERSON_MERGE_CONFLICT` with a `reason` (OQ-026).

## 20. Relationship archival transaction

Archiving a relationship:

```text
ACTIVE -> ARCHIVED
```

must:

- verify permission;
- verify optimistic version;
- update `archived_at`;
- increment version;
- create activity;
- create audit entry.

Derived kinship is not updated in storage because it is computed dynamically.

## 21. Claim Person transaction

A user claiming a Person requires:

```text
membership ACTIVE
person ACTIVE
person.family_id == membership.family_id
person.linked_user_id == null
no other non-MERGED person in family linked to current user
```

The operation sets:

```text
person.linked_user_id = currentUser.id
```

and writes audit/activity as applicable.

Creating a Person with `linkToCurrentUser = true` ("Start with me") applies the same rules in the transaction that creates the Person. When the current User already has a non-MERGED linked Person in the Family, the request is refused with 409 `USER_ALREADY_LINKED` and nothing is created; `uq_person_linked_user_per_family` is the final guard against concurrent requests.

Claiming the Person already linked to the current User changes nothing. A Person linked to another User is refused with 409 `PERSON_ALREADY_CLAIMED`; a User already linked to another non-MERGED Person of the Family with 409 `USER_ALREADY_LINKED`, and `uq_person_linked_user_per_family` is the final guard against concurrent claims.

Unclaim sets `person.linked_user_id = null` and is allowed to the linked User (any role) and to an ADMIN; on a Person linked to nobody, an ADMIN's unclaim changes nothing and anyone else is refused (OQ-009).

Admin unclaim is an audited operation.

## 22. Duplicate detection

Duplicate detection is advisory.

Candidates are selected with the deterministic rule of `product/domain/person-relationships-collaboration.md` §4.1, on normalized values of:

```text
first_name
last_name
preferred_name
birth year
```

The database does **not** impose a uniqueness constraint on names or birth data.

Creating a probable duplicate is allowed after explicit user confirmation.

## 23. Query patterns and indexes

### 23.1 Family people search

Expected query fields:

```text
family_id
status = ACTIVE
first_name / last_name / preferred_name
```

Matching is case- and accent-insensitive (`product/mvp.md` §19). The `unaccent` extension is created in its own migration (`V005__unaccent.sql`, `genealogy.md` §11). The query filters on `family_id` and `status` (index `idx_persons_family_status`) and compares `lower(unaccent(...))` of `first_name`, `last_name`, `preferred_name` and `first_name || ' ' || last_name` with a `LIKE` pattern; it orders by `lower(unaccent(display name)) COLLATE "C"`, `created_at`, `id` (OQ-022). `unaccent` is not `IMMUTABLE`, so there is no expression index: the Family filter is enough for small/medium family sizes (a 250-Person Family is covered by a smoke test).

If usage requires it, PostgreSQL `pg_trgm` can be enabled later without changing the domain model.


## 24. Database responsibilities vs domain responsibilities

### Database must guarantee where practical

```text
foreign-key integrity
same-family references through composite foreign keys
self-relation prohibition
single linked user per family
active relation uniqueness
basic date representation consistency
```

### Domain/application must guarantee

```text
permissions
parental acyclicity
probable-date warnings
linked-person edit protection
merge semantics
minimum one related Person per Memory
Person lifecycle rules
membership-based data isolation at API/use-case level
```

## 25. Physical deletion

Normal product flows do not physically delete:

```text
persons
relationships
memories
memberships
```

Permanent deletion required by privacy/compliance processes is a separate administrative capability and must explicitly handle referential integrity, audit policy and object-storage deletion.

It is not part of the standard MVP user API.

## 26. Migration strategy

Use Flyway migrations.

Example:

```text
backend/src/main/resources/db/migration/
  V001__extensions_and_types.sql
  V002__users_and_families.sql
  V003__memberships_and_invitations.sql
  V004__persons.sql
  V005__relationships.sql
  V006__media_and_memories.sql
  V007__activity_and_audit.sql
  V008__indexes_and_constraints.sql
```

Rules:

- committed migrations are immutable;
- a schema change requires a new migration;
- production data must never rely on Hibernate `ddl-auto=update`;
- production should use schema validation only.

## 27. ORM guidance

JPA entities are infrastructure persistence models, not the domain model.

Recommended direction:

```text
Domain Person
    ↕ mapper
PersonJpaEntity
```

Avoid exposing lazy JPA associations across application boundaries.

Prefer explicit repository queries for graph traversal and API projections.

## 28. MVP data-model definition of done

The persistence layer is ready when automated integration tests prove at least:

1. two families cannot be connected by a relationship;
2. a person cannot relate to itself;
3. duplicate active explicit relationships are impossible;
4. partner relation canonicalization prevents reverse duplicates;
5. a user can be linked to only one non-merged Person per Family;
6. archived and merged Persons remain recoverable/queryable internally;
7. memories can reference multiple Persons without duplication;
8. a Person merge is atomic;
9. optimistic concurrency detects stale updates;
10. family-scoped queries cannot leak data across Families;
11. an invitation token can be accepted only once, and never after expiry, revocation or renewal;
12. a Family can never be left without an ACTIVE ADMIN;
13. removing a membership releases the member's linked Person in the same transaction.
